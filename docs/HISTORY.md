## A. 阶段实测（原 FRAMEWORK §5）

**原则：脚本测试好一切，再进行编程。** 分阶段推进，前一阶段不通过不进入后一阶段。

### A.1 阶段一实测记录（PowerShell）

**结论：窗口持有者、DPI、提权、前台四项前提逐一核实；其中两项当场改写了不变量。**

| 靶子 | 实测 | 结论 |
| --- | --- | --- |
| 窗口持有者 | `pythonw.exe` pid=60388 持窗；`ok-ww.exe` 不在进程表 | 复核「窗口持有者」= `pythonw` |
| 窗口类 / 标题 | `Qt6111QWindowIcon` / `OK-WW v3.6.7 China  - OK-WW` | 与 E.1 逐字一致 |
| 子窗口数 | `EnumChildWindows` = **0** | 纯 Qt 自绘，无控件树可定位 |
| 窗口尺寸 | 采样 12 次恒定 `1200×800`；另一时刻实测 `1500×1000` | **非自发漂移，是事件性变化** |
| 窗口句柄稳定性 | 同一 ok-ww 先后 `9834000`、`198446142`、`55771756` | **句柄每次运行都不同（INV-14）** |
| DPI | `GetDpiForWindow` = **120**（1.25×）；`LOGPIXELSX`=120；`GetDpiForMonitor`=120 | T-1 解决：ok-ww 是 DPI 感知的，不存在逻辑尺寸换算层 |
| 缩放变化响应 | 125%→150%：120→144，rect `1500×1000`→`1800×1200`，位置 `646,188`→`408,55` | T-7 解决：**立即反映，无需重启** |
| 坐标系 | 物理 2560×1440；DPI 虚拟化 2048×1152（1.25× 时） | 抓图与点击必须做此换算（见 [FRAMEWORK.md](./FRAMEWORK.md) §1.1） |
| 提权状态 | ok-ww `TokenElevation` = **已提权**；框架 `IsAdmin` 未提权时 False，以管理员重启后 True | INV-7 前提亲测证实；进程链见 B.1 |
| 前台 | ok-ww **不在前台**（前台为 Chrome） | 前台约束的场景成立 |
| 多实例 | `pythonw` 同时有 ok-ww 与 ok-nte 两个实例 | 由「独占式」消解 |

**另有一条瞬时故障**：某次读取时 class 被读成 `Q`、title 被读成 `O`（均截断为 1 字符），同批 `GetWindowRect` 数值正常，后续读取恢复 ⇒ 判为**瞬时故障**，不写成约束。

### A.2 阶段一补充实测：抓图通道

**结论：抓图通道定为「屏幕抓图」；`PrintWindow` 与「API 说可见」双双被证伪。**

| 靶子 | 实测 | 结论 |
| --- | --- | --- |
| PowerShell 全屏抓图 | 2560×1440 PNG，240KB，肉眼可见内容正常 | **采用此通道** |
| `PrintWindow` 抓 ok-ww | 返回 `ok=False`，产出 1500×1000 **全黑**图（5945 字节） | INV-13 新增 |
| 窗口可见性 | API 报 `visible=True`，而全屏截图中 ok-ww **不在屏幕上** | INV-12 新增 |
| 遮挡成因 | 用户确认是把 DSH 窗口置于前面所致；实际使用中不会发生 | 记为前置条件，非缺陷 |
| `desktop_capture` | 5 次调用（handle / region / window / outPath）全部失败：`Error: tool result must be losslessly JSON-serializable`，失败在**返回**结果阶段（`desktop_list_windows`、`desktop_diagnose` 均正常） | 工具故障，已停用；改用 PowerShell / `ctypes` 通道 |

**INV-12 的意义**：`IsWindowVisible` 返回 True **不代表窗口真的显示在屏幕上**。真实光标只能点屏幕上真实存在的东西，故抓图后必须校验帧内容（非全黑、含预期特征），不能只信 API 布尔值。

### A.3 阶段一收尾实测：提权相关

**结论：提权改变的是「跨完整性级别」的判定，两条旧不变量的表述被当场改写。**

前置：DSH 以管理员身份重启后 `IsAdmin = True`。

**INV-11 — 投递窗口消息**（只在语义为空的 `WM_NULL (0x0000)` 上验证，不投真实点击消息）：

| 调用 | 返回值 | 判读 |
| --- | --- | --- |
| `PostMessage(hwnd, WM_NULL, 0, 0)` | **True** | 投递成功 |
| `SendMessage(hwnd, WM_NULL, 0, 0)` | 0 | 成功（`WM_NULL` 语义返回 0） |
| 窗口 rect（前/后） | 1200×800 → 1200×800 | 窗口状态未被改变 |

对照：框架**未提权** → ok-ww 提权时 PostMessage 报 `(5, '拒绝访问。')`（E.2.1）；框架**已提权** → 成功。
⇒ **INV-11 的「必然失败」表述被证伪**，改为「成败取决于完整性级别是否匹配」。

**INV-7 — 进程终止权限**（先探测权限、后实际执行）：提权会话杀自起的 `notepad` 成功；`OpenProcess(PROCESS_TERMINATE)` 对 ok-ww 返回有效句柄；`Stop-Process -Force` 成功；善后无残留 `pythonw`。未提权时 `OpenProcess`/终止均 Access denied（E.2.2）。
**副作用（如实记录）**：ok-ww 被终止是经用户授权的**故意代价**。

**INV-16 — `GetLastError` 不可作成败判据**：上述实验中调用**已成功**（`PostMessage` 返回 True、`OpenProcess` 返回有效句柄），而 `GetLastError` 仍是 **203**（`ERROR_ENVVAR_NOT_FOUND`）—— P/Invoke 未先清零，读到的是无关调用的残留。

### A.4 阶段二：Python — 图像与点击

**结论：帧尺寸与内容两道校验在 Python 侧成立；负向对照同时暴露了三条静默失效。**

**环境**：`D:\WORKs\Anaconda\python.exe`（Python 3.13.9），已装 Pillow 12.0.0、numpy 2.3.5、win32gui、win32api；无 cv2 / pyautogui / mss。（系统另有 `C:\Python314`，四个库全无，不可用。）抓图用 `ctypes` + `BitBlt`，匹配用 numpy 归一化互相关。

**当时建的探测脚本**（`../probe/`）：

| 文件 | 作用 |
| --- | --- |

| `verify_negative.py` | 负向对照：证明校验器**真的会失败**（现位于 `../legacy/probe-investigation/verify_negative.py`） |

**已通过的验证**：

| 靶子 | 实测 | 判定 |
| --- | --- | --- |
| T-5：帧尺寸 == 窗口 rect | `1500×1000 == 1500×1000` | T-5 通过 |
| 抓帧耗时 | **16–18 ms**（1500×1000） | 可用于实时循环 |
| 内容校验 | 均值 RGB (52,52,52)，25 种采样色彩 → 放行 | 校验器工作 |
| 肉眼确认 | 帧内可见标题栏、版本号 v3.6.7、更新日志、左侧栏 | **身份确认**；该帧即第一层「检查更新」页，与 T-3「启动按钮在第一层」一致 |

**负向对照（关键：证明校验器会失败）**：

- **N-1 尺寸错配**（通过）：故意以 `1200×800` 抓一个 `1500×1000` 的窗口，校验器正确报出不一致。而该错配帧的内容统计是**完全「健康」**的 `均值(54,54,54) / 27 色` ⇒ **INV-1 必须独立于内容校验**：尺寸错的帧看起来毫无异常。
- **N-2 内容校验的边界**（暴露缺陷）：抓 ok-ww **之外**的屏幕区域，`150×150`、均值 `(21,21,23)`、6 色 → 被**放行**为「有内容」⇒ 内容校验只能筛「全黑」，**判不了帧里是谁**（INV-18）。
- **N-3 离屏抓帧**（暴露缺陷）：

| 抓取区域 | 结果 | 判读 |
| --- | --- | --- |
| 屏内 `(100,100)` | `80×80` 均值 (50,51,53)、43 色 | 正常 |
| 右越界 `(2500,100)` | `200×80` 均值 (6,6,7)、3 色 | 近黑 |
| 完全离屏 `(10000,10000)` | `80×80` **均值 (0,0,0)、1 色** | **未报错** |
| 负坐标 `(-500,-500)` | `80×80` **均值 (0,0,0)、1 色** | **未报错** |

⇒ `BitBlt` 对越界区域返回成功、`GetDIBits` 也返回行数，于是窗口外的抓帧**静默产出全黑帧**（INV-17）。

**静默失效汇总**（当时一次成型的清单；现行不变量全表见 [FRAMEWORK.md](./FRAMEWORK.md) §1）：

| 处 | 表现 | 拦截手段 |
| --- | --- | --- |
| INV-1 | 尺寸错配 → 点偏 | 帧尺寸 vs 窗口 rect 比对 |
| INV-12 | 窗口被遮挡 → 点空 | 抓图后内容校验 + 前台判定 + **身份校验** |
| INV-13 | `PrintWindow` → 全黑 | 改用屏幕抓图通道 |
| INV-17 | 越界抓帧 → 全黑而不报错 | 抓帧前校验坐标屏内 + 内容校验 |
| INV-18 | 抓到别的窗口 → 看似正常 | **只能靠模板匹配**（图像库） |
| INV-19 | 空白区不设约束 → 匹配到同构空行（**0.8476 假阳性**） | 只用鉴别性锚点 + 交叉验证 |
| INV-22 | 置前台报成功但窗口最小化 | 校验 rect 与帧内容 |
| INV-23 | 点击落在遮挡窗口上 | **目标顶层判定** |
| INV-24 | 锚点歧义 → 匹配到同款图标（**差 0.006**） | 锚点唯一性检查，拒绝而非赌 |
| INV-25 | 界面状态改变排版 → 行位置漂移 | 每次重新定位，不缓存坐标 |

**共性**：它们都**不抛异常、不返回错误码**，只给出错误结果。**最重要的一条经验**：抓图与匹配都必须在每一步验证「我操作的是不是我以为的那个东西」——本框架开发期间因缺这一步产生过多次错误结论（见 A.5 实测五、A.8 两次自纠）。

### A.5 阶段三：真实点击与模板定位

**结论：真实光标落点精度成立；同时确认前台判定是硬前置，并暴露出整行模板假阳性、右对齐按钮不可推算、任务栏按钮不可定位三件事。**

**已通过的验证**：

| 靶子 | 实测 | 判定 |
| --- | --- | --- |
| T-8 坐标落点精度 | 侧栏图标 窗口内 `(29,230)` → 屏幕 `(600,330)` → **命中预期图标，页面跳转** | T-8 通过 |
| T-2 前台重判 | 点击把焦点交给了**遮挡在上的 DSH**，ok-ww 失去前台 | T-2 = **必需** |
| 点击副作用 | 窗口尺寸未变（1500×1000 前后一致） | — |

**实测一：窗口尺寸在本阶段再次变化**。先后观测到 `1200×800` → `1500×1000` → `1875×1250`，且**在一次测量过程中就变了**；位置从 `(408,55)` → `(571,100)`。⇒ **每次操作前都必须重新读取窗口 rect，不得缓存。**

**实测二：整行模板的假阳性（INV-19 的来源）**。`2_ww.png`（1366×41，「每日任务 … 开始」行的局部截图，用户提供）横向结构：

| 区段 | x 范围 | 内容 |
| --- | --- | --- |
| 文字段 | 9..451 | 📅 每日任务 + 描述文字 |
| 空背景 | 452..1215 | **约 760px 无鉴别信息** |
| 按钮段 | 1216..1313 | 「▶ 开始」按钮 |

| 方法 | 分数 | 位置 | 判定 |
| --- | --- | --- | --- |
| **整行匹配** | 0.8520 | `(508,792)` | **假阳性** —— 裁图证实是**一条空行 + 开始按钮**，无「每日任务」文字 |
| **仅用文字段匹配** | **1.0000** | `(104,92)` | 正确：正是窗口顶端那一行 |

0.852 是「看起来不错」的分数。若据此点击，会点在**另一条任务的「开始」**上，而不报任何错。模板的原生尺度为 **1.00**（未缩放），与「同尺寸窗口下的局部截图」一致；此前「模板不同源」的怀疑**已撤回** —— 问题在**匹配方法**，不在模板。

**实测三：「开始」按钮右对齐，不能由模板偏移推算**。用模板内「按钮中心 − 文字起点」偏移（=1255）推算 → 预测 `(1359,112)` → 交叉验证亮像素占比 **0.000**，该处根本没有按钮。原因：窗口从 1366 宽变为 1875 宽，而按钮**右对齐到行末**，随窗口变宽右移 ⇒ 模板内的像素偏移不可迁移（INV-4 的直接实证）。
成功的做法：① 用**文字段**定位该行（`score=1.0000` @ `(104,92)`，行中心 y=112）；② 在**同一 y 带**内向右扫描高亮块，取最右块 `x=1686..1783, y=93..131`；③ **交叉验证**按钮中心 y=112 落在行 y=92..133 内。结果：「开始」按钮 窗口内 `(1734,112)`、尺寸 `97×38` → 屏幕 `(2305,212)`。

**实测四：任务栏按钮无独立窗口句柄（INV-20 的来源）**：`Shell_TrayWnd` hwnd=65952、rect `(0,1380)-(2560,1440)`；可见子孙窗口仅 **7** 个；`MSTaskSwWClass` / `MSTaskListWClass` rect 仅 `(1143,1380)-(1363,1440)`（220×60，是**容器**）；标题含 `OK-WW` 的任务栏窗口 **0 个** ⇒ 任务栏应用按钮由 DirectUI 绘制、**无独立句柄**，只能视觉定位，且位置随图标增减变化，属**不稳定资产**。
⇒ **决策（INV-20）**：前台切换改用 `SetForegroundWindow`（本阶段实测成功、零风险、不移动鼠标），图像识别与点击**只用于目标窗口内部**。

**实测五：前台与遮挡的实际行为（INV-12 最强实证）**：点击目标窗口内部时，若 DSH 窗口遮挡在上，点击会**把焦点交给 DSH**，目标反而失去前台；随后抓到的「目标帧」实为 **DSH 的画面** —— 尺寸正确、内容非黑、**通过了内容校验**，只有模板匹配分数暴跌（1.0000 → **0.5303**）才暴露。⇒ `IsWindowVisible=True` + 内容非黑**都不足以**保证帧里是目标程序 ⇒ **新增要求**：点击前须确认目标屏幕坐标处**最顶层的窗口**是目标程序，而不仅是「目标程序在前台」。
**另有一次自纠**：曾把「点击后帧差异 25.63」解读为「点击生效」，实际那帧是 DSH 画面；真正的生效证据是后续置前台后抓到的页面内容。**结论正确、依据错误 —— 已更正。**

**实测六：`SetForegroundWindow` 报成功但窗口不可用（INV-22 的来源）**：

```
SetForegroundWindow 返回 = True
GetForegroundWindow()      = 651954484   ← 正是目标窗口
但 IsIconic(hwnd)          = True
且 rect = (-32000,-32000)-(-31840,-31972)  160x28   ← 最小化哨兵值
```

⇒ 成功返回值 + 前台句柄一致，**都不能证明窗口可用**。这次执行是被 **INV-13 全黑帧检查**拦下的（帧 160×28 近乎全黑），证明该校验有实战价值。事后 `ShowWindow(hwnd, SW_RESTORE)` 成功还原（rect 恢复 `1875×1250`），**但早先同一调用曾失败过**，故不可假定 `SW_RESTORE` 必然有效，须校验结果。

**实测七：端到端执行成功**。七道校验全过后点击「每日任务 · 开始」：发现窗口 hwnd=651954484（1875×1250）→ 置前台且 `GetForegroundWindow == hwnd` → 帧尺寸 1875×1250 == rect、均值 (49,49,49)、36 色 → 文字段 `score=1.0000` @ `(104,92)` → 同行扫描按钮 x=1686..1783、中心 `(1734,112)` → 交叉验证通过 → `(2305,212)` 处顶层 = 目标 → 点击执行，点击后目标仍持前台、仍存活。

### A.8 阶段六：锚点歧义与等待状态

**结论：任务卡在等待条件时永不退出；锚点歧义从「日历图标」改成「每日任务」四字后端到端成功；自动关闭随之确证。本节含两次自纠。**

**实测十三：任务卡在等待条件，不会自动退出**。观测到一个真实运行中的每日任务（用户自行启动）：

| 字段 | 值 |
| --- | --- |
| 横幅 | `已完成: 📅 每日任务 已运行: 0h 1m 32s` |
| `current task` | `wait main esc=True` |
| 日志 | `claim daily reward via coordinate` |
| `current daily progress` | 0 |

关键证据：计时器**冻结在 `1m 32s` 不变**（跨约 4 分钟多次采样，指纹完全一致）⇒ 任务不是缓慢推进，而是**完全停顿**，等待一个不会到来的条件（进入大世界 + 组队）。
⇒ 目标程序**不会因条件不满足而超时退出**，会无限等待 ⇒ 框架不能假设它会自己结束，必须自行判定「完成 / 失败 / 超时」并具备中止能力。
⚠️ **当时「自动关闭」仍未验证**：本次任务从未跑完，故「跑完后自动关闭」没有被触发；此前基于「端到端后 `pythonw` 消失」的推断**证据不足，已撤销**。

**实测十四：锚点歧义 —— 「日历图标」不足以定位（INV-24 的来源）**。用户指出进度面板的日志行 `已完成: 📅 每日任务 已运行: …` 中**也含日历图标**，与模板里的图标相同，可能抢走匹配。实测（在同一帧内统计**全部** `score >= 0.85` 的位置，而非只取最高分）：

| 锚点 | 尺寸 | 高分位置数 | 位置一 | 位置二 |
| --- | --- | --- | --- | --- |
| **日历图标** | 17×41 | **2 个** | **1.0000** @ `(231,570)` | **0.9939** @ `(273,79)` |
| 日历+每日 | 36×41 | **2 个** | 0.9618 @ `(232,570)` | 0.9012 @ `(273,79)` |
| **每日任务四字** | 37×41 | **1 个** | 0.9225 @ `(257,570)` | — |

两个候选的裁图**肉眼无法区分**（同为日历图标 + 「每日」二字），分数仅差 **0.006** ⇒ **只取最高分是不安全的**；开发中使用的锚点 `tpl[:, 9:9+98]`（日历起头）本身即含歧义。
**对策（INV-24）**：① 锚点须**足够长且独特**（如「每日任务」四个字）；② 命中后做**唯一性检查** —— 存在第二个高分位置就**拒绝**，而非赌一个。

**实测十五：界面状态改变排版（INV-25 的来源）**：「每日任务」行 y 在**无进度面板**时为 **92**，**有进度面板**（任务运行中）时为 **570** ⇒ 进度面板使任务列表**整体下移约 478px**，行位置不是常量，每次都必须重新定位；这也解释了模板内固定像素偏移为何完全不可用。

**两次自纠（如实记录）**：

1. **「端到端执行成功」的表述过度**。准确说法：点击**可能**成功，但任务是否由我启动无法确认 —— 观测到的运行中任务是用户自行启动的，且锚点存在歧义（实测十四），不能排除点击落空。
2. **一次 2 分钟的观测是无效的**。当时目标失去前台，抓到的是**遮挡窗口**，截图里甚至能看到本对话的文字，「面板稳定」是假稳定；改用**带身份校验**的观测脚本重做后结果可信。

**教训**：抓图**不验证身份**，就会一本正经地分析错误的画面（INV-12 / INV-18 / INV-23 的又一实例）。

**实测十六：锚点歧义修复后，端到端执行成功**。锚点由「日历起头」（`tpl[:, 9:9+98]`，**2 个候选**）改为「每日任务」四字（`tpl[:, 35:72]`，**1 个候选**）。修正后九道校验全过：窗口发现 + 置前台验证（hwnd=21827074，1822×1000，前台）→ 帧尺寸 1822×1000 == rect → 内容非全黑（均值 (49,49,49)、30 色）→ **身份校验**（侧栏在 `(16,215)`，score=1.0000）→ 锚点 `0.9225` @ `(257,570)` → **锚点唯一性**（仅 1 个候选，旧锚点为 2 个）→ 同行扫描按钮 + 交叉验证（`(1682,589)`，y 落在行 570..611 内）→ 目标顶层判定（`(2132,644)` 处顶层 = 目标）→ 点击执行。
**点击生效验证**：横幅由 `已完成 … 1m 32s` 变为 `运行中: 📅 每日任务 已运行: 0h 0m 7s` —— **计时器从 0 重新开始**，证明这是一次**全新的运行**，而非旧任务的残留显示（旧任务计时器冻结在 1m32s 不动）。

**实测十七：自动关闭已确证**。运行 **1 分 22 秒**后，同一帧内同时出现三条通知：`Daily Task Completed` / `成功执行任务, 正在退出游戏和App!` / `Game Exited`；状态表为 `日志 = 每日任务已完成`、`current task = in main esc…`、横幅 `已完成 … 0h 1m 22s`（另有一条非致命错误 `MergeEchoTask Failed找不到对话框左侧按钮`，不影响完成判定）。随后 `pythonw` 消失 —— **自行退出**。

```

  → 通知「成功执行任务, 正在退出游戏和App!」
```

⇒ 文案「正在退出游戏和App」表明这是**设计行为**，不是崩溃；「任务跑完后自动关闭」= **已确证**。
**对先前的更正**：本节「两次自纠」中曾**撤回**「端到端执行成功」的结论。本次实测表明 **第一次端到端执行实际上确实生效了**，当时看到的运行中任务**确为我所启动**。撤回的理由（锚点存在歧义、无法排除点击落空）**在逻辑上仍然成立**，但**事实结论上判错了** —— 锚点歧义是真实缺陷（已由 INV-24 修复），只是那一次并未导致落空。

### B.1 提权与进程链（INV-7 / INV-11 的关键前提）

**实测进程链（DSH 由 explorer 启动时）**：

```
explorer.exe (13484)
  └ DSH Desktop.exe (58788)      ← 由 explorer 启动 ⇒ 未提权
      └ node (57372)
          └ node (67004)
              └ powershell (我)   ← IsAdmin = False
```

**DSH 以管理员身份重启后**：`IsAdmin = True`（父链为 `node ← node ← DSH Desktop`）。

**关键实测**：ok-ww（pid=60388）的 `TokenElevation` = **已提权** ⇒ 这就是 UIPI 冲突的机制来源：框架未提权而目标提权，**跨完整性级别**，窗口消息必然被拒（INV-11）。

**方法论教训**：`IsAdmin` 读的是**当前进程的令牌**，不是「用户会话的权限」。用户手动提权自己的终端**不会**让框架进程提权；**必须是 DSH 本身以管理员启动**，权限才能沿进程链继承下来。

### B.2 程序之间的过渡（INV-42 的证据）

**实测**：ok-nte 在 **ok-ww 退出后立即启动**时，置前台 **4 次尝试全败**；而**单独启动**同一程序则**第 1 次成功**。

⇒ 成因是**前台锁**在前一窗口刚消失时**短暂拒绝焦点切换** ⇒ **对策**：目标之间须**显式等待**，不能立刻置前台。

**意义**：这是**编排层**特有的约束 —— 单程序运行时不会遇到。既然最终目标是「按顺序启动多个程序」，这条必须在编排里落地。

### B.3 清理的「血缘已断」回退（ok-nte 发现）

**问题**：清理若按**进程血缘**（父→子）识别第二层 `pythonw`，则当**第一层先退出**后血缘关系**丢失**，第二层 `pythonw` **无法按血缘识别** —— 清理会漏掉窗口持有者。

⇒ **对策**：`../orchestrator/cleanup.py` 加「**残留有窗口**」回退（实测生效）：血缘查不到时，改为找**仍持有窗口**的 `pythonw`。

## E. ok-ww 窗口结构与鼠标点击事实记录（原根目录同名文件，附录）

实测日期 2026-10-01；测量环境 Windows 11（Build 26200）、本机 DPI 缩放 1.25×、ok-ww v3.6.7。原文「一、」「二、」即 E.1、E.2，原文 2.1–2.5 即 E.2.1–E.2.5。

### E.1 窗口结构

```
ok-ww.exe  (Tauri 外壳，启动后退出/隐藏)
  └─ pythonw.exe   pid=52140  400MB      ← 真正的应用，窗口持有者
       hwnd=9834000
       class = Qt6111QWindowIcon
       title = 'OK-WW v3.6.7 China  - OK-WW'
       尺寸  = 1200x800（首次）/ 1375x900（1.25x DPI 下）
       children = 0                        ← 零子窗口，纯 Qt 自绘
```

**实测结论：**

1. **`pythonw.exe` 不是孤儿，是真正干活的进程。** `ok-ww.exe`（第一层）启动后退出或转后台，窗口由 `pythonw` 持有。按进程名清理时必须保留 `pythonw`。
2. **窗口标题是长串，不是 `'OK-WW'`。** 框架对字符串 title 做**精确相等**比较，`'OK-WW'` 匹配不上 `'OK-WW v3.6.7 China  - OK-WW'`；非 str 才走 `re.search`，所以必须编译成正则（标题里是**两个空格**）。
3. **零子窗口 + 纯自绘。** 没有可定位的按钮句柄，也没有标准控件树。
4. **窗口尺寸会变。** 实测同一窗口先后出现 `1375x1000`、`1200x800`、`1375x900`。抓图与点击若跨了尺寸变化，**算出的点击坐标就是错的**。实测反例：1372 宽的模板在 1375 宽的帧里匹配成功，但窗口实际只有 1200 宽。

**DPI 缩放**：本机为 1.25×。窗口逻辑尺寸 1100×720 时，实际 rect 为 1375×900。抓图与坐标换算必须考虑这一点（现行取值见 B 节测量环境表）。

### E.2 鼠标点击

#### E.2.1 两套方式的实测对照

| 方式 | 机制 | 实测结果 |
| --- | --- | --- |
| `PostMessage` | `win32gui.PostMessage(hwnd, WM_LBUTTONDOWN/UP, ...)` | 从**非提权**会话向提权的 ok-ww 投递 → `(5, 'PostMessage', '拒绝访问。')` |
| 真实光标 | `SetCursorPos` + `SendInput` | 成功移动光标 |

#### E.2.2 UIPI 是关键约束

Windows **UIPI**：低完整性进程不能向高完整性窗口投递窗口消息。

| 场景 | PostMessage |
| --- | --- |
| 提权程序 → 提权窗口 | 允许 |
| 非提权程序 → 提权窗口 | **被拒（Access denied）** |
| 任意 → 同/低完整性窗口 | 允许 |

**真实光标（`SendInput`）走输入队列，不受 UIPI 限制** —— 这是它与 PostMessage 的本质区别。

ok-ww 是 `requireAdministrator`，由此得到三个实测事实：

- **操作方必须以管理员运行**，否则 PostMessage 被拒
- 非提权脚本**无法**向它投窗口消息
- 非提权会话**也杀不掉它**（实测 `Stop-Process` → Access denied）

#### E.2.3 「窗口必须在前台」的实际后果

`Pynput` 方式的 `should_capture()` 等价于 `hwnd_window.is_foreground()`，即要求 `GetForegroundWindow() == hwnd`。

**这不只是「要求」，它会让上游框架整个卡死**（实测）。框架 `TaskExecutor.sleep()` 的分支：

```python
if not (self.paused or ... or not self.interaction.should_capture()):
    to_sleep = self.pause_end_time - time.time()
    if to_sleep <= 0:
        return                      # ← sleep() 唯一的正常出口
else:
    self._wait_for_activity(0.1)    # ← should_capture()=False 时走这里，无出口
```

窗口不在前台 → `should_capture()` 为 False → 走 `else` → **`sleep()` 永不返回** → `execute()` 主循环第一步即卡住 → **队列里的任务永远不被取出**。

**用户可见症状：点「开始」后毫无反应，且没有任何报错。** 线程真栈（实测抓取）：

```
execute      → sleep(1)
sleep        → _wait_for_activity(0.1)
_wait_for_activity → condition.wait(timeout)
```

同时 `paused=False`、`thread_alive=True`、`queue=1[...]` 连续 90 秒不变。

`PostMessage` 的 `should_capture()` 恒为 `True`，**不触发**此问题。

#### E.2.4 点击坐标

- 框坐标来自**抓图帧**，经 `ClientToScreen` 转为屏幕坐标。
- **帧尺寸必须等于窗口尺寸**，否则坐标错位（见 E.1 的尺寸变化问题）。
- 框内点击位置用**比例位置**表达：`relative_x` / `relative_y`，`0.5` = 居中，`0.85` = 靠右。
- 比例比像素偏移更稳 —— 不受模板尺寸与窗口缩放影响。

#### E.2.5 其他实测事实

- **真实光标会移动鼠标**，且目标窗口需在前台。
- 提权环境下会额外出现一条报错（与识别无关、不影响功能）：`pywintypes.error: (5, 'GetCursorPos', '拒绝访问。')` —— 来自无边框窗口插件取光标位置被拒。

## F. 2026-10-22 节点链拆到每个程序

### F.1 为什么拆

链条原先只有一份全局声明：`orchestrator/steps/main.py` 的 `CHAIN`（1/2/4/5/6/7/8/9）、`context.py` 按它算下一步、`gui/chain.py` 再抄一份 `STEPS`。三个程序跑同一串节点，看起来是框架不变量，其实只是**三个程序的巧合**：
