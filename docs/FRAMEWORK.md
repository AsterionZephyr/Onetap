## 0. 定位与边界

| 项 | 结论 | 依据 |
| --- | --- | --- |
| 与 ok-ww 的关系 | **黑盒**。ok-ww 是他人项目，只做进程外操作，不改造其源码 | 用户决策 |
| 交互方式 | **仅真实光标**（`SetCursorPos` + `SendInput`） | 用户决策 |
| PostMessage | **记录在案的未采用路线，不实现**。理由见 ADR 0001 | HISTORY E.2.1 §2.2 |
| 图像库的性质 | **资产**。以图像为核心，记录该图像对应区域需要点击的位置 | 用户决策 |
| 板块数 | **三块**（程序链条 / 识别与操作 / 图像库），不设第四块 | 用户决策 |
| **目标程序数** | **四个**：三个**操作型**（MaaEnd（zmd）、ok-ww、ok-nte；ww/nte **结构同构**（INV-28），MaaEnd 单层）+ **FOS（fos）**，后者**没有可编排的界面**：只启动 + 等它自己退出，全程不识别、不操作 | §0.1、§0.1.3 |
| 最终目标 | **按顺序启动这些程序完成任务** | 用户决策 |

**为什么不用 PostMessage**：它虽然能免掉前台约束（§2.3），但在 UIPI 下非提权进程投递被拒（§2.1 `(5, 'PostMessage', '拒绝访问。')`），而 ok-ww 是 `requireAdministrator`（§2.2）。真实光标走输入队列不受 UIPI 限制。此取舍见 `docs/adr/0001`。

> **后经实测修正**：提权框架向提权 ok-ww 投递 **可以成功**（HISTORY A.3）。不采用的理由因此收窄为「真实光标跨完整性行为一致、不依赖窗口消息语义」，**而非「投递不可用」**。详见 INV-11 说明。

**链条属于每个程序**：清单写在 `orchestrator/apps/<key>/nodes/__init__.py`，声明节点**数量、编号、顺序**
与每节的实现归属（`shared`）；主控（`steps/main.py` / `context.py`，经 `steps/chain.py`）与 GUI 都只按清单执行。
目标由 `--target` 选择（`orchestrator/programs.py:ALL` 是唯一来源，`gui/targets.py` 的 FALLBACK 只是界面兜底）。
`python -X utf8 -m orchestrator.steps.main --list` 按程序逐份打印链条（顺序 = `ALL`）。

⇒ 加第 N 个程序：在 `programs.py` 加一条 `Program` + `orchestrator/apps/<key>/__init__.py`
+ `orchestrator/apps/<key>/nodes/__init__.py`（+ 需要的专属节点文件），**不改 `main.py` / `context.py` / GUI 代码**。
节点数、编号、顺序随程序：ww/nte/zmd **三份恰好都是八节**，FOS 是**四节**（1,2,3,9）。
见 [ADR 0005](./adr/0005-per-program-node-chain.md)。
⚠️ 新增程序还要同步两处**非代码清单**：`gui/targets.py` 的 `FALLBACK`（GUI 兜底）与
`orchestrator/apps/__init__.py` 的 `ADAPTERS`（懒 import 入口）；漏了前者 GUI 里看不见它，漏了后者
`apps.get(key)` 抛 `KeyError`。

**执行顺序不是写死的**：`ALL` 只给**默认**顺序（MaaEnd → ok-ww → ok-nte → FOS）。实际顺序由
`--target` 的**书写顺序**决定，GUI 的 ↑/↓ 改的就是它（见 [GUI.md](./GUI.md) §2.1）。
本表其余各行是「实测事实」，覆盖范围以「当前实现」列为准。

→ 真实光标点击前必须过 INV-8/INV-23。
**差异**分布在四处：**进程与窗口标识**（exe／窗口类／标题／层数）、**界面布局**（侧栏序号／锚点／按钮色）、
**判据模块**（终态判据／游戏进程名／日志目录）、**节点清单**（每程序自己声明跑哪几节、哪些节点专属，

> ⚠️ **MaaEnd 打破了两条「两程序同构」的直觉**（2026-10-18 实测）：
> ①**单层** —— 没有 `pythonw` 第二层，窗口由 `MaaEnd.exe` 自己持有，故节点 4/5 的「排除第一层」
> 那套双重闸对它不适用，靠 `window_class == "Tauri Window"` **精确相等** + 进程归属来识别；
> ②**有伴生进程** —— `agent/go-service.exe`、`agent/cpp-algo.exe` 是它拉起的子进程（同属 `zmd` 目录），
> 而 `msedgewebview2.exe`（在 `Program Files`）**不可**纳入归属，否则会误杀系统里的 WebView2。

**「执行模型」一行的重要性**：ok-nte **v1.4.8 起与 ok-ww 同构** —— 由早期的「单行日常任务 + 右下角唯一
一个开始按钮」改为**逐任务行**（每行一个「开始」，实测 **9 个同款按钮**）。
⇒ 这正是本框架**不可依赖固定按钮模板**的原因：同款按钮必然歧义，动作元素必须由**行结构扫描**得出
（见 §4.3）。

> 该方案建立在一个**现已不成立的前提**上：ok-nte「全页仅一个开始按钮，位于右下角」。
> v1.4.8 改版后该前提消失，副锚点 `2_nte.png` 因 **9 个同款按钮**而必然歧义

### 0.1.3 FOS（fos）—— 第 4 个程序：只启动，不操作

> 用户裁定（2026-10-23）：**"该程序只需要启动，之后等待就行，它自己会退出并清理干净，全程不需要
> 任何识别、操作；所以也不要去深扒它的运行逻辑。"** 本节就是这条裁定的落地形态。

| 项 | 结论 |
| --- | --- |
| 可执行文件 | `E:\TOOLS\ScriptsGames\MPA\FOS.exe`（单文件 PyInstaller，**单层**，无 pythonw 第二层） |
| 我们要做的只有两件 | **启动**（节点 2，共用 `step2_launch`）；**等它自己退出**（节点 3，专属 `apps/fos/nodes/step3_wait_exit.py`）。**不抓帧、不识别、不动鼠标、不置前台** |
| 节点 3 的判据 | **只读进程表**（`apps/fos/__init__.py::fos_processes`）：连续 3 次采样在 MPA 目录下看不见进程 ⇒ 已退出 ⇒ `result=completed`；启动后**一次都没看到**进程 ⇒ FAILED（多半启动即失败）；超过 `--wait-timeout`（默认 **5400s**）⇒ TIMEOUT（由节点 9 决定怎么收） |
| 为什么不看窗口 | 它自己会退出并清理干净，界面无需干预；研究它的界面/逻辑属**明确不做**的事 |
| 归属范围 | `programs.FOS.process_prefix` 取**整个 MPA 目录**（不是 `data/apps/<name>`）：PyInstaller 运行期会把子进程（如 `MFWUpdater.exe`）散在目录各处。MPA 里没有被编排的其它程序，故放宽前缀**不违反 FAULT #32**（`programs.self_check()` 逐对验这条） |
| 两个「刻意的空字段」 | `loose_title_re` / `ready_title_re` / `min_width` / `min_height` 在 FOS 上**永远不会被用到**（从不 `find_window(fos)`）。看到有人拿它们判身份，那是 bug |
| 为什么没有 4/5/6/7 | 那四节是「等窗口持有者 / 等就绪 / 抓首帧校验 / 置前台」，都依赖**要操作的窗口**。FOS 没有 ⇒ 这四节在它的链上**根本不存在**（不是暂时禁用） |
| dry-run | 节点 3 在 `--dry-run` 下**照常等待**：等待不是操作；提前返回会把还在跑的 FOS 带进下一轮 |
| 上限為何是 5400s | 实测一轮 **4379s（≈73 分钟）** 才自然退出（HISTORY 第 9 轮，`run-20261023-055917`）⇒ 取 90 分钟留 ~23% 余量。`programs.FOS.run_timeout=5400.0` 与 `apps/fos.WAIT_TIMEOUT_SECONDS=5400.0` **必须同值**：前者是主控 per-program 的 `--run-timeout` 默认，后者是节点 3 自己的闸；任一更小都会提前掐掉，而 GUI 不暴露这两个参数 |

## 1. 不变量

框架的全部约束收敛为以下条目。**任何一条被破坏，框架必须停手告警，不得继续用可疑数据算坐标。**

| # | 不变量 | 依据 | 状态 |
| --- | --- | --- | --- |
| INV-1 | **帧尺寸必须等于当次窗口 rect**。不一致时绝不用该帧计算点击坐标 | HISTORY E.1 第 4 条、§2.4 | 已证实 |
| INV-2 | **窗口尺寸会变**：同一窗口实测先后出现 `1375×1000`、`1200×800`、`1375×900`、`1500×1000`、`1800×1200` | HISTORY E.1 第 4 条；本次实测见 HISTORY A.1 | 已证实 |
| INV-3 | **模板匹配成功 ≠ 坐标有效**。1372 宽模板可在 1375 宽帧中匹配成功，而窗口实际只有 1200 宽 | HISTORY E.1 第 4 条（实测反例） | 已证实 |
| INV-4 | **图像资产必须携带其出生尺寸**，匹配成功时须校验资产出生尺寸与当前窗口 rect 同源 | 由 INV-3 推出，Q1=(d) 决策 | 设计决定 |
| INV-5 | **窗口标题需正则匹配**，不可用 `'OK-WW'` 精确相等。框架对 str 做精确相等，非 str 才走 `re.search` | HISTORY E.1 第 2 条；本次实测见 HISTORY A.1 | 已证实 |
| INV-6 | **按进程名清理时必须保留 `pythonw.exe`**。它不是孤儿，是窗口持有者 | HISTORY E.1 第 1 条；本次实测见 HISTORY A.1 | 已证实 |
| INV-7 | **操作方必须以管理员运行**。非提权会话杀不掉 ok-ww；提权会话可以。**这是框架的硬前置**，不是优化 | HISTORY E.2.2（非提权被拒）；本次实测见 HISTORY A.3（提权成功） | ✅ **双向复核完成** |
| INV-8 | **真实光标路线下窗口必须在前台**（`GetForegroundWindow() == hwnd`），**且每次点击前须重新判定**，不得复用上一次结论。**更进一步**：须确认目标坐标处最顶层的窗口是 ok-ww（INV-23） | HISTORY E.2.3；本次实测见 HISTORY A.5（T-2 = 必需） | ✅ **已证实** |

**⚠️ 同类错误第二次（「点首行 = 执行错任务」）**：曾据一次观测判定「编排固定点 ok-nte 任务页第一行 → 只跑了「异象界域」」。
后用**完整运行的日志**证伪：
```
success=['一咖舍','日常领取','影院约会','喷泉签到','异象家具','羁遇赠礼']
failed=['异象界域']  skipped=['异象追猎']
```
⇒ 跑的是**完整日常任务集合**，`异象界域` 只是**恰好失败**的那一项；点首行「开始」是**启动入口**，跑什么由程序内部勾选配置决定。

**共同模式**：两次都是「**看到了真实现象，却给出了错误的原因**」。
⇒ **规则**：对"为什么"的断言，必须找到一个**能同时解释所有观测**的原因才算成立；
只有一个观测支持时，只能记为「现象」而非「原因」。

**INV-1 的第一号地位**：它是唯一一条「算错了也能点下去、且点歪了不报错」的约束。其余各条失效时通常伴随显式失败，INV-1 失效时表现为**静默点错位置**。

**INV-12 / INV-13 / INV-17 / INV-19 / INV-23 与 INV-1 同类**：都是**静默失效** —— 不报错、不崩溃，只是点空、抓到黑图、或点在错误的目标上。它们是本框架的**主要失效模式**，构成「必须主动校验」的一组。

**INV-19 的严重性**：假阳性分数 **0.8520** 是一个「看起来很好」的分数。若据此点击，会点在**另一条任务**的「开始」上而**不报任何错**。⇒ **分数阈值不是充分的保护，必须有独立的交叉验证**（见 HISTORY A.5 实测三）。

**INV-11 的修正说明（重要）**：原文写「**禁止**投递窗口消息，它**必然失败**」，**该表述已被实测证伪**。提权会话向 ok-ww 投递 `WM_NULL` **成功**（HISTORY A.3）。真实规则是完整性级别匹配与否：

- 框架未提权 + ok-ww 提权 ⇒ 被 UIPI 拒绝（HISTORY E.2.2 实测）
- 框架提权 + ok-ww 提权 ⇒ **允许**（本次实测）

**但结论不变：框架仍不采用投递路线。** 理由是 ADR 0001 的取舍（真实光标不受 UIPI 限制、行为跨完整性一致），而非「投递必然失败」。**这是一个理由被修正、结论保持不变的例子** —— 记录下来以免后人误以为前提是「投递不可用」。

### 1.1 关于 DPI 的更正（重要）

**ok-ww 是 DPI 感知的**，启动时显式声明 per-monitor DPI 感知（用户源码调研结论），本次实测 `GetDpiForWindow(ok-ww) = 120`（即 1.25×）佐证。窗口界面文字**不模糊**，观察一致。

**因此不存在「隐藏的 1.25 倍缩放因子」**。曾经出现的 `1200×800 × 1.25 = 1500×1000` 是**巧合**：那是同一窗口在**两个不同时刻**的两种真实尺寸，属 INV-2，而非缩放关系。**此前的「会点偏 25%」推论已撤回。**

**坐标系事实（本次实测）**：

| 坐标系 | 尺寸 | 说明 |
| --- | --- | --- |
| 物理像素 | **2560 × 1440** | DPI-aware 进程所见；截图即此坐标系 |
| DPI 虚拟化坐标 | 2048 × 1152 | DPI-unaware 进程所见（1.25× 时 = 2560 ÷ 1.25） |

**框架一律使用物理像素**，且抓图与坐标换算须在同一 DPI 感知级别下进行。

## 2. 板块一：程序链条

**定义**：程序链条 = 多个程序按顺序启动并执行任务。它描述**条件与顺序**，不描述底层实现。识别与点击的细节归板块二。

### 2.1 关键结构：ww/nte 是两层，MaaEnd 是单层

```
第一层  ok-ww.exe  / ok-nte.exe   → 检查更新 / 启动准备   ← 自动放行，约 21 秒
第二层  pythonw.exe               → 真正工作的程序（窗口持有者）
```

**ww/nte 结构同构**（INV-28）：`ok-nte.exe`（Tauri）实测同样**自行退出**，第二层同样是 `pythonw`。
窗口类与标题不同，见 §0.1。

> ⚠️ **MaaEnd 是单层**（2026-10-18 实测）：`MaaEnd.exe` 拉起后**不退出**，窗口由它自己持有
> （`class='Tauri Window'`，标题 `MaaEnd v2.34.0-beta.1`），**没有** `pythonw` 第二层。
> ⇒ 节点 2 的「启动第一层」与节点 4 的「等待窗口持有者出现」对它是**同一件事**；
> `programs.ZMD.has_second_layer=False` 让节点 4 只等窗口出现、不再等「第二层」。
> 其子进程 `agent/go-service.exe`、`agent/cpp-algo.exe` 只在执行任务时起，属进程血缘追踪范围。

**关于 hwnd**：HISTORY E.1 记的 `hwnd=9834000` 只是一个**历史观测值**。本次实测同一 ok-ww 先后出现 `198446142`、`55771756`、`651954484`、`21827074`（见 INV-14）。**hwnd 必须每次运行重新发现，不得写入任何资产或配置。**

**关于 ok-nte**：本机实测 `pythonw` 可同时存在多个实例（本次见到 ok-ww 与 ok-nte 各一）。框架为**独占式**（INV-15）：同一时间只运行两者之一，运行完将相关进程全部清理。

#### T-4 结论：第一层会**自动放行**，人工点击只是**加速**（本次实测）

实测启动时间线（**全程未点击任何东西**）：

| t | 事件 |
| --- | --- |
| 1.0s | `ok-ww.exe` 起（Tauri Window 1393×1047，标题 `ok-ww`） |
| 21.5s | `pythonw` 出现（内存 2.5 MB） |
| 23.3s | `pythonw` 涨至 215 MB |
| 25.2s | **Qt 窗口出现**（`Qt6111QWindowIcon`，标题 `OK-WW`） |
| ~27s | **`ok-ww.exe` 进程消失**，Qt 窗口变为 1875×1250 |

⇒ **不点击也能进入第二层**，无需人工干预，耗时约 **21–27 秒**。
⇒ **修正**：先前表述隐含「不点就过不去」，**该表述不成立**。人工点击的真实作用是**节省约 21 秒的等待**，而非跨过一道必经关卡。
⇒ HISTORY E.1 的「`ok-ww.exe` 启动后退出/隐藏」，其精确机制是：**第一层自动放行后退出**。

**对框架的意义**：节点 3 从「必经的人工关卡」降级为「**可选加速**」。框架可以**完全无人值守地等待第二层出现**，这使全自动流程成为可能。

**ok-nte 侧确认**：`ok-nte.exe` 同样**自行退出**，第一层自行放行 ⇒ 节点 3 在两程序上**行为一致**。

### 2.2 节点清单：每程序一份，骨架共用

**链条属于每个程序**：清单写在该程序的 `orchestrator/apps/<key>/nodes/__init__.py` 里，
元素是 `Node(sid, name, label, why, has_args, shared)`，声明**数量、编号、顺序、每节用哪份实现**。
主控与 GUI 都只按清单执行：`--only/--from/--to` 的编号是**该程序自己的**节点编号，
不在该程序清单里的编号直接拒绝。ww/nte/zmd 三份都是八节（1、2、4、5、6、7、8、9，**共用编号里没有 3**），
FOS 那份是四节（1、2、3、9 —— 它的 3 是**自己的**「等它自己退出」，与缺号无关）。
**节点数不要求相同**：FOS 就是只有四节的现实例证，引擎一行都不用改（[ADR 0005](./adr/0005-per-program-node-chain.md)）。

**共用骨架**在 `orchestrator/steps/common/`，**不认识具体程序**（不出现 `ww`/`nte`/`zmd`）；
程序差异只经**钩子参数**传入：

| 节点 | 共用骨架 | 程序差异（钩子） |

### 2.2.1 节点 5 的两个必备子步骤（**均由 ok-nte 首次暴露**）

节点 5 不是「等到窗口出现」这么简单。ok-nte 的接入实测暴露了两个**两程序通用**的坑：

**其一：窗口发现必须排除第一层**（INV-32）。

`find_window` 按标题子串匹配时，**第一层与第二层会被同一子串命中**：

| 层 | 类名 | 标题 | 是否被 `ok-nte` 子串命中 |
| --- | --- | --- | --- |
| 第一层 | `Tauri Window` | `ok-nte` | ✅ **会被命中** |
| 第二层 | `Qt6112QWindowIcon` | `ok-nte v1.4.8 China  - ok-nte` | ✅ 会被命中 |

⇒ 编排曾取到**第一层**，导致身份校验失败。
⇒ **对策**：`find_layer2()` —— **按窗口类排除 `Tauri Window`**，或要求长标题。

**其二：窗口出现 ≠ 界面可用**（INV-31）。

ok-nte 在窗口出现后仍覆盖 **「正在启动, 120秒后超时.」** 遮罩，此时界面元素**尚未渲染**，
任何匹配都会失败（实测 **0.4344**）。ok-ww 侧同样存在启动期界面未就绪的窗口。

⇒ **对策**：`wait_until_ready()` —— 要求**身份锚点连续 3 次可匹配**才算就绪。
⇒ 修复后就绪等待从 **180s 超时**降到 **6 秒**。
⇒ 这也是 §4.4「身份锚点必须页面无关」的由来：就绪判定与身份校验**复用同一个锚点**。


### 2.3 节点 3：「跨过第一层」

**当前实现：人工；性质为「可选加速」。** 本期**不实现自动识别点击**（决策 Q3=(c)），仅保留位置与前置条件，接口不冻结。

- **位置**：节点 2 与节点 4 之间。**已确定**（T-3 已解决）。
- **前置条件**：第一层已启动。
- **成功判据**：第二层窗口出现（即节点 4 的进入条件成立）。
- **失败处置**：**不需要处置** —— T-4 实测证明**不点击也会自动放行**（约 21 秒）。本节点失败（没人点）的后果只是**多等约 21 秒**，不是卡死。
- **将来替换为自动时的契约**（现在不实现，仅留位）：
  - 输入：当前帧 + 前台状态
  - 资产：需在图像库中登记**启动按钮**图像及其点击位置
  - 输出：成功 / 失败 / 未知 **三态**
  - 失败处置：失败或未知时**不得继续**，须停手并报告
  - **收益仅为省时**：因 T-4 已证明不点也能继续，此功能的唯一价值是**缩短约 21 秒**，而非解锁流程。

**位置问题（已关闭）**：T-3 确认**启动按钮在第一层中**。
⇒ 本节点确定位于 **2 与 4 之间**，在**第二层窗口出现之前**就需要被点击。
⇒ **推论**：该点击**不能**依赖「第二层窗口就绪」的前置校验（节点 5、6、7 全部尚未成立）。它是本链条上唯一一个**在校验缺省状态下点击**的动作 —— 这是本期不实现它的额外理由。
⇒ **但因 T-4，这一缺点的代价被大幅降低**：即便这个节点完全不实现，链条依然能走通，只是慢 21 秒。


### 2.4 已知故障：窗口不在前台会卡死整条链

HISTORY E.2.3 的实测：`should_capture()` 等价于 `hwnd_window.is_foreground()`，为 False 时 `sleep()` **没有正常出口**，`execute()` 主循环第一步即卡住，**队列里的任务永远不被取出**。

```
execute            → sleep(1)
sleep              → _wait_for_activity(0.1)
_wait_for_activity → condition.wait(timeout)
```

用户可见症状：**点「开始」后毫无反应，且没有任何报错。**

**这条对本框架的意义**：它是「前台判定」（节点 7）不是可选优化而是硬前置的原因。窗口失焦时，故障表现为**静默挂起**，而非报错。任何「点了没反应」的诊断，第一站都是前台状态。

## 3. 板块二：识别与操作

**定义**：从帧到点击的完整路径。执行视图 — 怎么点、点歪了怎么办。链条板块只写「何时、在什么条件下」。

### 3.1 坐标链

```
抓帧  →  模板匹配得到框  →  由资产取框内比例位置  →  ClientToScreen 转屏幕坐标  →  SetCursorPos + SendInput
   ↑                              ↑
INV-1 在此拦截              INV-4 在此拦截（资产出生尺寸校验）
INV-13 在此拦截（帧全黑即中止）
```

**实测的坐标换算（本次，hwnd=55771756，1500×1000）**：

| 帧内点 | `ClientToScreen` 结果 |
| --- | --- |
| Client(0,0) | Screen(646,188) |
| Client(600,400) 中心 | Screen(1246,588) |
| Client(1020,400) `relative_x=0.85` | Screen(1666,588) |

换算关系为**平移**：`Screen = Client + 窗口左上角`。**无缩放因子**（见 §1.1）。

### 3.2 点击坐标的表达

- 框坐标来自**抓图帧**，经 `ClientToScreen` 转为屏幕坐标（§2.4）。
- **帧尺寸必须等于窗口 rect**，否则坐标错位（§2.4、INV-1）。
- 框内点击位置用**比例**表达：`relative_x` / `relative_y`，`0.5` = 居中，`0.85` = 靠右（§2.4、INV-9）。
- **比例优先的理由**：不受模板尺寸与窗口缩放影响（§2.4）。

### 3.3 前台约束

- 真实光标会移动鼠标，且**目标窗口需在前台**（§2.5、INV-8）。
- 失败表现为**静默挂起**，见 §2.4。
- **确认必需**（T-2 实测）：点击会把焦点交给**遮挡在上的窗口**，ok-ww 反而失去前台。故**每次点击前必须重新判定前台**。
- **更进一步**：仅判前台不够，须判**目标坐标处最顶层的窗口**是 ok-ww（INV-23）。

### 3.4 匹配分数的阈值（实测依据）

同一模板（`2_ww.png` 文字段）在本环境的分数分布：

| 场景 | 分数 | 说明 |
| --- | --- | --- |
| 正确页面 + 侧栏**收起** | **1.0000** | 像素级完全一致 |
| 正确页面 + 侧栏**展开** | **0.9402** | 布局偏移导致亚像素差异 |
| **错误页面** | **0.4722** | 目标根本不存在 |

**阈值建议**：

| 区间 | 处置 |
| --- | --- |
| `>= 0.90` | 接受 |
| `0.85 ~ 0.90` | 告警，**必须**交叉验证后才可点击 |
| `< 0.85` | 拒绝 |

**⚠️ 不要用 0.95**：正确页面在**侧栏展开**时会降到 0.9402，会被**误拒**。本框架开发期间就因此误拒过一次。
**⚠️ 阈值不是充分保护**：整行匹配在**错误行**上仍给出 0.8476（见 INV-19），故必须配合交叉验证（§3.1、§4.3）。

**侧栏展开/收起会影响内容区布局**，这是分数波动的真实来源，属**正常现象**而非故障。


### 3.5 窗口尺寸与 DPI（T-1、T-7 均已解决）

**T-1 结论：ok-ww 是 DPI 感知的**（启动时显式声明 per-monitor DPI 感知；本次实测 `GetDpiForWindow = 120` 即 1.25×；界面文字不模糊）。

**因此不存在「逻辑尺寸换算」这一层。** 窗口 rect 就是它的物理像素尺寸，抓图帧尺寸**直接**与窗口 rect 比对即可（INV-1）。原「以逻辑尺寸 `1100×720` 为锚」的口径**作废**，理由见 §1.1。

**当前口径**：

- **窗口尺寸是外生变量**（INV-2）：实测同一窗口在 `1200×800`、`1500×1000`、`1800×1200` 之间变化，变化由窗口自身/用户/缩放设置引起，框架无法预测。
- **不做「期望帧尺寸」的先验推算**，改为**每次抓图后读取窗口 rect 并与之比对**：帧尺寸 ≠ 当次窗口 rect 时停手（INV-1）。
- 远程控制软件（本机为 GameViewer）会**改变缩放比例**。缩放一旦变化，窗口 rect 随之变化，由 INV-1 自然拦截，**不需要单独处理**。
- **基线尺寸的用途**改为**仅用于资产归属判定**（INV-4）：资产记的是「出生时窗口多大」，与当前 rect 比对，不同源则拒绝点击。

#### T-7 结论：缩放变化时窗口 rect 立即反映，无需重启 ok-ww（本次实测）

| 探针 | 125% | 150% |
| --- | --- | --- |
| `LOGPIXELSX` | 120 | **144** |
| `GetDpiForWindow(ok-ww)` | 120 | **144** |
| 窗口 rect | `1500 × 1000` | **`1800 × 1200`**（= ×1.2） |
| 窗口位置 | `646,188` | **`408,55`**（重新居中） |

**推论（重要）**：窗口尺寸可被框架**完全无法感知的外部操作**（有人改系统缩放）改变，且**成比例整体变化**（连位置一并重算）。故 INV-1 的逐帧校验**不可省略**：此刻用旧尺寸帧算出的坐标会错 **20%**。

**另一实测发现**：DPI-aware 进程看到的 `HORZRES` / `SM_CXSCREEN` 恒为 **2560×1440**（物理），与 `LOGPIXELSX` **相互独立**。即「物理分辨率」与「缩放比」是两个正交的量 —— 缩放变化不改物理分辨率，只改 DPI 与窗口 rect。这修正了 §1.1 中「虚拟化坐标 = 物理 ÷ 缩放」的表述精度：该关系对 **DPI-unaware 进程**成立（2560÷1.25=2048、2560÷1.5≈1707），**对 DPI-aware 进程不成立**。

### 3.6 已知的良性报错（不作为故障处理）

HISTORY E.2.5 记载，提权环境下会额外出现一条报错：

```
pywintypes.error: (5, 'GetCursorPos', '拒绝访问。')
```

来自无边框窗口插件取光标位置被拒。框架不得将此类报错计入失败判定。

#### T-6 结论：该报错**不可复现**，且**结构上不可能影响核心链路**（本次实测）

**其一，不可复现。** 在提权会话（`IsUserAnAdmin = True`）中：

| 调用 | 结果 |
| --- | --- |
| `GetCursorPos`（ctypes，3 次） | **全部成功**，`pos=(2255,929)`，`err=0` |
| `GetCursorPos`（pywin32，即事实记录中报错的路径） | **成功** |

⇒ 事实记录把该报错描述为「提权环境下的伴随现象」，**这个因果关系不成立**。它是**特定条件**下的偶发现象（很可能与无边框窗口插件当时的状态有关），而非提权的必然结果。

**其二，「良性」的判断得到结构性验证。** 该报错与核心链路是**完全独立的两条路径**：

| 功能 | 调用的 API | 是否读光标 |
| --- | --- | --- |
| 抓图 | `GetDC` + `BitBlt` + `GetDIBits` | ❌ 不涉及 |
| 定位 | `GetWindowRect` / `ClientToScreen` | ❌ 不涉及 |
| 点击 | `SetCursorPos` + `SendInput` | ❌ **写**光标，非读 |

`GetCursorPos` 是**读**光标的独立路径，本框架**一次都不使用**。
⇒ 故排除它是**结构性保证**，不依赖经验观察。**判据：凡报错来源为 `GetCursorPos` 的，一律不计入失败判定。**

### 3.7 导航：按「内容簇序号」而非绝对 y

**两程序的任务页都在侧栏，但 y 不同**（ok-ww ≈230，ok-nte ≈329）。
⇒ **不可硬编码绝对 y**：侧栏行距**随窗口高度缩放**（ok-ww 实测 1823×1000 下任务项 y≈230；
1458×800 下 y≈**183**）。

⇒ **对策**：改用**内容簇序号**（0-based）—— 先扫描侧栏得到图标簇，再取第 N 个：

| --- | --- | --- |
| ok-ww | **index 2** | 230 |
| ok-nte | **index 3** | 329 |

**ok-nte 侧栏固定收起**：实测点左上 ☰ **无法展开**侧栏（x>60 区域是**主内容区**，非侧栏标签）。
⇒ 「靠侧栏文字标签定位」这条路**在 ok-nte 上走不通**（属其固有设计，不是点击失败）。
⇒ 但用**页面标题文字**（页面锚点）达到了同样效果且更贴近内容，是更好的方案。

## 4. 板块三：图像库

**定义**：以图像为核心的**资产**。每条资产记录：这张图像 + 它对应区域**需要点击的位置**。

### 4.1 资产条目结构

| 字段 | 内容 | 依据 |
| --- | --- | --- |
| 图像 | 模板图本身 | 用户决策 |
| 点击位置 | **比例** `relative_x` / `relative_y` | INV-9、§2.4 |
| **出生尺寸** | **采集该资产时的窗口尺寸** | INV-4、Q1=(d) |
| 用途 | 该资产服务于哪个节点 | §2.2 |

### 4.2 出生尺寸的作用

**INV-3 的实测反例必须被自动拦截**：*1372 宽的模板在 1375 宽的帧里匹配成功，但窗口实际只有 1200 宽。*

若资产上写着「我出生在 1200×800 的窗口里」，框架在 1375 宽帧上匹配成功时即可判定**帧与资产不同源**并拒绝点击 —— 而不是等点歪之后才发现。

**为什么不用绝对屏幕坐标做校验位**：屏幕坐标会随窗口移动而失效，出生尺寸不会。故采用「比例 + 出生尺寸」而非「比例 + 绝对坐标」。

### 4.3 两级锚点架构（**两程序统一**）

> **这是本框架最终的定位架构**，ok-ww 与 ok-nte **完全一致**。

```
身份锚点 identity  →  确认「这一帧是目标程序、且界面已就绪」
页面锚点 page      →  确认「在哪一页」（并给出该行的 y）
动作元素 action    →  在行内「点哪里」
```

**为什么必须是两级而非一级**：ok-nte 的实测暴露了这一点（INV-26）——
**同一个按钮会在多个页面出现**（实测「开始」在 **3 个页面**出现）。
仅凭按钮**无法确定在哪一页**，只凭文字则知道在哪页但不知道按钮在哪。**缺一不可**。

**为什么动作元素不注册为固定模板**：两程序的动作元素都位于**行末**，且**同款按钮在一帧内重复出现**
（ok-nte v1.4.8 实测 **9 个**同款「开始」）。固定模板**必然歧义**。
⇒ 故 `action=None`，改由 **行结构扫描**（`find_ww_action` / `find_nte_action`）得出：

| 步骤 | 动作 |
| --- | --- |
| 1 | 用**页面锚点**定位该行（须**唯一**） |
| 2 | 在同一 y 带内扫描高亮按钮块，取**最右**者 |
| 3 | **交叉验证**：按钮中心 y 必须落在行范围内 |

**两程序在此仅有一处参数差异**：按钮高亮色 —— ok-ww 为**白**（亮度 > 200），ok-nte 为**青**
（`B/G > 150` 且 `R < 130`）。这是 `_scan_row_button(mode="white"|"cyan")` 的全部区别。

**行模板的关键限制**：

- 行内元素（如右对齐的按钮）位置**由当前窗口宽度决定**，**不能**由「模板内偏移」推算（INV-21）。
- 行模板中的空白段**不产生约束力**，整行匹配会退化为结构匹配（INV-19）。
- **锚点必须唯一**（INV-24）：界面上可能有视觉几乎相同的候选，只取最高分不安全。
- **行位置随界面状态变化**（INV-25）：进度面板出现时列表整体下移，故每次都要重新定位。

#### 4.3.1 页面锚点单独不可靠（**ok-nte 发现的第三类假阳性**，INV-33）

判定「已经在目标页」时，**页面锚点会单独给出假阳性**：ok-nte 的**「关于」页**上，
`3_nte_daily`（「日常任务」文字）曾得 **0.9373** —— 编排因此误判"已在任务页"而**跳过导航**，
随后动作元素找不到，流程失败。

⇒ **判据修正**：判定「在目标页」必须**同时满足页面锚点命中 且 动作元素命中**。
⇒ 修复后正确输出「页面锚点命中=True，动作元素命中=False → 尝试导航」。

### 4.4 身份锚点：必须页面无关且唯一

**身份锚点承担两件事**：① 确认帧确实来自目标程序（INV-18）；② 判定界面已就绪（INV-31）。
故它必须**在任何页面都能匹配到、且唯一、且不随加载状态变化**。

**ok-nte 上连续踩坑 3 次**（这段历史是「不要凭坐标手工裁剪」这条规则的来源）：

| 尝试 | 结果 |
| --- | --- |
| `3_nte_daily`（「日常任务」文字） | ❌ 「关于」页得 0.4224 —— 程序启动**不在任务页** |
| `1_nte`（原侧栏图标） | ❌ 新 UI 上仅 0.5096，且**有 2 个候选** |
| 手工裁 ☰（按坐标 y=20..40） | ❌ 实际裁到了 **← 返回箭头**，得 0.4339 |
| **程序化定位 ☰** | ✅ **1.0000，唯一，跨重启稳定** |

**ok-ww 上同样的坑**：曾用 `1_ww.png`（侧栏 ▶ 图标）当身份锚点 ——
它在窗口尺寸 **1458×800**（实测出现的**最小尺寸**）下只得 **0.3962**，
因为该尺寸下侧栏图标更小、位置不同，导致就绪等待 **180s 超时**。

⇒ **两程序的最终方案相同**：**左上角 ☰ 菜单图标**（`3_ww_menu.png` / `4_nte_menu.png`），
实测 **1.0000 且唯一、页面无关**，属**窗口固定元素**。

**⚠️ 不要用固定的 ☰ 截图当身份锚点**（INV-38）：程序启动后会**异步加载用户头像**等元素，
左上角像素随之改变；同一程序同一尺寸下 ☰ 模板实测从 1.0000 掉到 **0.55**。
⇒ 应改用**程序化特征检测**（找**三条等距水平亮线**），`assets.json` 中的 ☰ 仅作**回退**。
