## ✅ FAULT #11 已修复 —— 导航点了 ☰（**我自己引入的回归**）

**现象**（第 1 轮末与第 2 轮首次跑）：节点 8 的 `[8a]` 连点 3 次侧栏图标，
ok-ww **一直停在「关于」页**，最终 `INV-24：导航 3 次后仍未进入任务页`。

**取证**：`shots/002-task-loop-start.png` 与 `004-nav-attempt2.png`
**画面完全相同**（ok-ww v3.7.4「关于」页），证明点击**完全没效果**。
日志里 `侧栏图标窗口内中心=(30,71) -> 屏幕 (773,368)` —— **(30,71) 正是 ☰ 的位置**。

**根因**（`step8_run_task.py:117-123`）——导航点击目标**复用了身份锚点的 pos**：

```python
sidebar = registry["sidebar_tasks"]; tpl = sidebar.load()
ident = match.verify_identity(frame.rgb, tpl)     # ← 改造后返回的是 ☰ 的位置！
th, tw = tpl.shape[:2]
cx = ident["pos"][0] + tw // 2                    # 17+13 = 30
cy = ident["pos"][1] + th // 2                    # 56+15 = 71
```

改造前 `verify_identity` 返回的是**侧栏「任务」图标**位置（`1_ww.png` 匹配），
所以这个复用**恰好成立**；我把身份锚点改成 ☰ 检测后，`pos` 变成 ☰ 的坐标，
导航于是**点到了 ☰**（只切换侧栏显隐，页面不变）——**不报错，只点错地方**，
是本仓库 6 类静默失效里的典型一例。

> 这正是 `FAULT-LOG` 早先写下的警告：
> 「`1_ww.png` 曾**同时承担两个职责** —— 身份校验锚点 **+ 导航点击目标**」。
> 我改掉了其中一个，却沿用了另一个的返回值。

**修复**：新增 `match.find_sidebar_item(frame_rgb, index, log=None)`，
**程序化**定位侧栏第 index 项（0-based），不再依赖任何截图模板或绝对 y。

算法（纯结构，不含尺寸常量）：
1. 取侧栏横向窄带 `x=8..95`，按行统计亮像素，合并成文字行簇；
2. 丢掉 ☰ 自身（三行、总高 ≤12、位于上部 20%）；
3. 在剩余簇里找**最长的一段近似等距**序列 —— 那就是菜单列表
   （行距相对偏差 ≤ `SIDEBAR_PITCH_TOL=0.35`）；
4. 取该序列第 `index` 项；`SIDEBAR_ITEM_TASKS = 2`（截图方式=0，实时触发=1，**任务=2**）。

为什么不用模板：侧栏项里「任务」与**「计划任务」子串歧义**（后者含「任务」二字），
模板匹配易歧义；且绝对 y 随尺寸变（INV-39）。

## ⚠️ FAULT #18 —— ok-nte 判据的 `SUMMARY` 正则已被程序升级打死（**静默**）

**现象**（实测，非推测）：对 `ok-script.log`（10-15 00:23 那次成功的运行）
调用 `nte_verdict.extraction_summary()`，返回：

```
success = None
failed  = []
skipped = None
```

而同一个文件的 `verdict_from_log()` 却报「完成 7 项」⇒ **两者矛盾**。

**根因**：`probe/nte_verdict.py:46` 的
```python
SUMMARY = r"DailyRoutineTask:success:\s*(\[[^\]]*\])\s*failed:\s*(\[[^\]]*\])\s*skipped:\s*(\[[^\]]*\])"
```
期望**一行**里同时出现 `success: [...] failed: [...] skipped: [...]`。
但 ok-nte **从 v1.4.8 起改为三行独立输出**：
```
DailyRoutineTask:info_set success ['异象界域', '一咖舍', '日常领取', '影院约会', '喷泉签到', '异象家具', '羁遇赠礼']
DailyRoutineTask:info_set failed []
DailyRoutineTask:info_set skipped ['异象追猎']
```
实测 `re.search(SUMMARY, raw, re.S)` 返回 **`None`** —— **完全匹配不到**。
于是 `extraction_summary` 静默走 `if not m:` 分支，返回
`(None, extraction_failures(...), None)`；`failed=[]` 只是**碰巧正确**
（那次确实 0 失败），而 `success`/`skipped` 双双为 `None`。

**危害**：**被跳过的任务 `异象追猎` 被静默吞掉**；若某次运行真有失败项，
现象同样静默。这属于本仓库反复强调的**静默失效**一类。

**证据链（逐文件实测，`re.findall` 计数）**：

| 日志文件 | 老格式 `DailyRoutineTask:success:` | 新格式 `info_set success` |
| --- | --- | --- |
| ok-script.2026-10-08.log | 1 | 1 |
| ok-script.2026-10-09.log | 1 | 1 |
| ok-script.2026-10-10.log | 1 | 1 |
| ok-script.2026-10-11.log | 1 | 1 |
| ok-script.2026-10-12.log | **0** | 1 |
| ok-script.2026-10-13.log | **0** | 1 |
| ok-script.2026-10-14.log | 0 | 0 |
| ok-script.log（10-15） | **0** | 1 |

⇒ 10-08~10-11 是**过渡期**（同一毫秒两种格式都写，实测 23:15:31,774），
**10-12 起老格式彻底消失**。所以该正则在写成时是**正确的**，
是**程序升级让它静默失效** —— 与 INV-35（程序升级使资产过期）**同一类**，
只不过这次过期的是**文本解析**，不是图像。

**正确写法**（已实测可提取三条列表）：
```python
SUCC = r'DailyRoutineTask:info_set success\s*(\[[^\]]*\])'
FAIL = r'DailyRoutineTask:info_set failed\s*(\[[^\]]*\])'
SKIP = r'DailyRoutineTask:info_set skipped\s*(\[[^\]]*\])'
```
且**必须同时保留老格式**作为兼容分支（历史日志分析仍要用）。

### ★ `LogWindow` 为什么必须存在（防假阳性）

按 `ok:quit app` 分段会在「上一次运行被**外部强制终止**」时把两次运行
**合并成一段**（被强杀的那次不写 `ok:quit app`），于是新一次运行
**借用上一次的成功汇总** —— 实测在点击后 **1 秒**就报 SUCCESS，且不报错。
按**字节偏移**切窗口与上一次如何收尾**无关**。

`LogWindow.poll()` 必须处理三种情形（否则漏读或重读）：
文件**新出现**（日志轮转产物）⇒ 整体读；**变大** ⇒ 从旧偏移增量读；
**变小**（被轮转/截断）⇒ **整体重读**，不能只读差值。

### 判定只看「是否完成」

用户明确要求：**个别子任务失败与本项目无关，只看是否完成**。
失败详情由 `nte_failures()` 单独取出打印，**不参与判定**。

## ⚠️ FAULT #23 —— 点击生效判据「整帧均值」看不见局部响应（**已修复**）

**现象**（实机，非推测）：`run-20261016-011008` 跑 ok-nte 节点 8，

**根因**：`step8_run_task.click_and_confirm` 用
```python

if diff >= CHANGE_THRESHOLD:   # CHANGE_THRESHOLD = 0.5
```
「整帧**平均**像素差」当判据。而 ok-nte 的响应是**局部**的：
toast 只占全帧 **0.5%** 像素 ⇒ 整帧均值被摊薄到 **0.153**，永远够不到 0.5。

**实测数据**（逐像素复核，两次误判各一组）：

| 组 | 整帧均值 | 最大块差 | 变化>10 像素占比 | 差异位置 |
| --- | --- | --- | --- | --- |
| try1（003 vs 004） | 0.23 ❌ | **5.12** @块(7,7) | 0.44% | 右下「开始」按钮按下态 |
| try2（005 vs 006） | 0.15 ❌ | **3.20** @块(0,3) | 0.50% | 顶部 toast「启动成功」 |

⇒ 与 `match.find_menu_glyph` 那次**同型**：把「全帧统计量」当作
「事件已发生」的判据。**整帧均值对局部变化天生不敏感。**

**修复**（`orchestrator/steps/step8_run_task.py` 新增 `frame_changed(before, after, log=None)`）：

1. 整帧均值 >= `CHANGE_THRESHOLD` —— 原判据，覆盖**整页切换**（ok-ww 导航）；
2. **任一 8x8 块**均值 >= `CLICK_BLOCK_MIN = 2.0` —— 抓**局部响应**

3. 变化像素（|Δ| > `CLICK_PIXEL_DELTA = 10`）占比 >= `CLICK_PIXEL_FRAC = 0.002` —— 兜底。

另：帧尺寸改变也算变化（窗口重建）。日志现在打印**全部三个指标**，不再只给一个数。
新常量：`CLICK_BLOCK_ROWS = 8`、`CLICK_BLOCK_COLS = 8`、`CLICK_BLOCK_MIN = 2.0`、
`CLICK_PIXEL_DELTA = 10`、`CLICK_PIXEL_FRAC = 0.002`。

## ⚠️ FAULT #25 —— ok-nte 的 LogWindow 武装在**点击之后**，日志永远读不到（**已修复**）

**顺带确认 `poll()` 三分支是对的**（`orchestrator/verdict.py:220-252`）：

## ⚠️ FAULT #29 —— 抢前台是裸调，前台锁一挡就永久失败（**已修复**）

**怎么发现的**：FAULT #28 修复后的实跑验证（run-20261016-032240）里，
节点 8 活到了 137.5s（修复前只有 2.4s），但最后撞上：

```
[FAIL] 节点 8  run_task  137.5s  INV-8：连续 10 次未能把 ok-ww 置前台
```

**复现（决定性）**：让 DSH 自己的窗口占住前台，再调 `ensure_foreground`：

| 条件 | 结果 |
| --- | --- |
| DSH 窗口在前台 | **0/6 全失败** |
| DSH 不在前台 | 第 1 次就成功 |

⇒ 不是「API 不可靠」，是**前台锁**在起作用，而重试同一个被拒的调用
**永远不会成功**。

**根因**：`orchestrator/win32.py` 的 `set_foreground` 是裸调：

```python
def set_foreground(hwnd):
    return bool(user32.SetForegroundWindow(hwnd))
```

Windows 的前台锁规定：**别的进程持有前台时，SetForegroundWindow 被直接拒绝**。
`input.ensure_foreground` 会重试 10 次，但每次都调同一个注定失败的调用。
HANDOFF §5 写的是「SetForegroundWindow **并每次验证**」——
**验证那半句在，抢锁那半句一直没实现**。

**修复**：`set_foreground` 改为按优先级依次尝试三种手段：

1. **裸调** —— 最快，无人竞争时即可；
2. **AttachThreadInput**：把自己的线程输入队列附加到前台窗口的线程，
   使本进程被视为可抢占前台，再调 SetForegroundWindow，
   **并在 `finally` 里解除附加**（不解除会污染输入队列）；
3. **ALT 抖动**：`SendInput` 合成一次 ALT 按下/松开，让系统认为刚有用户输入，
   再调一次。

**验证**：用**真实鼠标点击**让 DSH 窗口占住前台（这是唯一能确定性拿到
前台的途径），再调 `ensure_foreground`：

| | 修复前 | 修复后 |
| --- | --- | --- |
| 成功率 | 0/6 | **3/3** |
| 耗时 | ~10s 后抛 INV-8 | **0.5s** |

**顺带修掉一个归因错误**：节点 8 开工前的稳定等待里，
「置前台失败」与「帧不可读」共用一个 `except GuardFailure`，
于是置前台连续失败时日志报的是

```
[警告] 等了 120s 画面仍未稳定（连续可读仅 0/3 次）
```

—— 把人引去查**游戏遮挡**，而真凶是**前台锁**。
两者都会让抓帧失败，但修法完全不同。现分开统计并分别报因：
拿不到前台时明说「这不是画面问题，是前台锁被别的窗口占着」，
并点名常见占用者（DSH 自己的窗口、浏览器）。

**教训**：这条与 FAULT #18/#20 同型 —— **「文档写了」不等于「代码做了」**。
HANDOFF 里那句「并每次验证」读起来像完整方案，实际只实现了后半句；
而前半句的缺失**只在有别的窗口抢前台时才暴露**，平时完全看不出来。

**新增探针** `probe/_probe_foreground.py`：静态 12 项（三种手段都在、
附加会被解除、绑定可用）+ live 抢前台实测（用真实点击制造竞争，
断言成功率）。live 段的注释里写明**为什么不能用 set_foreground 制造竞争** ——
那是「用假设失败的机制去搭测试台」，实测还会互相消耗 ALT 抖动的信用。

最终正常退出。**所以不能一见到 `pos_invalid` 就断定卡死。**

## ⚠️ FAULT #32 —— `force_close(program=None)` 不等于「全部」，它回落到 ok-ww（**已修复**）

**出现节点**：节点 9 / watchdog 的跨程序清理。**日期**：2026-10-16。

**现象**：`--target both` 一轮跑完，ok-nte 的 launcher 还在（pid 25736，7 个窗口）。
调 `force_close(None)` 想「都清掉」，它打印**「游戏进程已全部退出」** —— 进程仍在。
**这句话为真却误导**（它按 ok-ww 的名单查了，ok-ww 的游戏确实退干净了）。

**根因**：`program=None` 在实现里是「用默认程序」，`programs.DEFAULT` 是 ok-ww，
于是只按 ok-ww 的 `game_names`（`Client-Win64-Shipping.exe`）去枚举。
`None` 在 Python 里常被当成"通配"，这里是**恰好相反**的语义 —— 这种"看着像通配其实有默认值"
的签名，是静默失效的温床。

**处置**：跨程序清理必须显式 `all_programs=True`（`watchdog._force_close_all`）。
回归 `probe/_probe_force_close_all.py` 直接把这条语义钉住：`get(None)` 必须回落到 `DEFAULT`、
而 `DEFAULT` 不得是通配 —— 也就是说**它守的不是"能清干净"，而是"别拿 None 当全部"**。
该探针不杀任何进程（只做静态与桩判断），可以在任何机器上跑。

**来源**：`orchestrator/watchdog.py` 的 `_force_close_all`、`probe/_probe_force_close_all.py` 的模块 docstring、

## ⚠️ FAULT #34 —— `process_prefix` 只覆盖第二层，第一层启动器「隐身」且杀不掉（**已修复**）

**出现节点**：节点 1（窗口发现）/ `--pre-clean`。**日期**：2026-10-17 实机坐实。

**现象**（两个互相独立的后果，都很疼）：

1. **残留的第一层 shell 会劫持下一次运行**。ok-nte 的第一层是 Tauri 启动器，
   界面上就是「▶ 启动应用」按钮。上一次运行留下的第一层（实测 pid 26892，存活 48s 以上，
   命令行 `E:\TOOLS\ScriptsGames\ok-nte\ok-nte.exe`）持有**与第二层同名的窗口**
   （标题 `ok-nte`、类 `Tauri Window`）—— 窗口发现会认它，但它**不会替我们拉第二层**，
   只停在那里等人点按钮 ⇒ 后续所有节点对着一个"空壳"操作。
2. **框架看不见它，所以也杀不掉它**：`window.running()` 对第一层返回空
   ⇒ `--pre-clean` 与收尾都清不掉残留第一层 ⇒ **故障一轮一轮复现**，
   而且每次都"看起来是新的"。

**根因**：归属判据 `process_prefix` 指的是 `data/apps/<name>/`（**第二层**的安装目录），
而第一层 exe 装在 `root_dir` 下、prefix **之上**：
ok-nte 第一层 `E:\TOOLS\ScriptsGames\ok-nte\ok-nte.exe` vs prefix `...\ok-nte\data\apps\ok-nte`
⇒ `owns_process(第一层) == False`。

**处置**：判据从「单个前缀」放宽为「**前缀列表**」——

- `process_prefix`（第二层，**精确**匹配）保持不变；
- 再加 `root_dir`（第一层），但必须**再按 exe 名收窄**：拿共同父目录
  `E:\TOOLS\ScriptsGames\` 当判据会连带杀掉对方的第一层 = **#32 型事故**。

`programs.self_check()` 里加了一条断言守着这件事，回归
`probe/_probe_first_layer_ownership.py`（145 行，含"**绝不认对方的第一层**"的反向用例）。

**来源**：`orchestrator/programs.py` 的 `Program` 定义与 `self_check()`、

## ⚠️ FAULT #37 —— `state.json` 的原子替换撞上 GUI 的读轮询 ⇒ `WinError 5`（**已修复**）

**出现节点**：任何写 `state.json` 的节点（几乎每个）。**日期**：2026-10-18 实测。

**现象**：节点跑着跑着抛

**根因**：Windows 上「原子替换」与「有别的进程在读」**互斥**。

撞车对象就是**自己家的 GUI**：它每 120 ms 读一次 `state.json` 画进度。
实测撞车率 **6.9%~7.8%**（`probe/_probe_state_race.py`：8840 次替换里失败 613 次）。

**处置**：`RunState.save()` 加重试 —— **12 次退避**（[RUNBOOK.md](./RUNBOOK.md):237）。
同一夹具换成重试实现后 **0/8060** 失败。
回归 `probe/_probe_state_race.py --verify-fix`（`--raw` 作负向对照，能看到它确实会撞）。
修好后首次由用户亲手在 GUI 点「两个都跑」，两轮全绿
（[GUI.md](./GUI.md):398，2026-10-18 14:06:41，`run-20261018-140641`）。
