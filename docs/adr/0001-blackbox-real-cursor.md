# 1. 黑盒进程外操作，且只用真实光标

日期：2026-10-01

## 状态

已接受

## 背景

需要在 ok-ww 上自动执行任务。ok-ww 是他人项目，且以 `requireAdministrator` 运行。

事实记录（[ok-ww-窗口结构与鼠标点击-事实记录.md](../../ok-ww-窗口结构与鼠标点击-事实记录.md)）实测了两条互斥的操作路线：

- **`PostMessage`**：`win32gui.PostMessage(hwnd, WM_LBUTTONDOWN/UP, ...)`。从非提权会话向提权的 ok-ww 投递，得到 `(5, 'PostMessage', '拒绝访问。')`（§2.1）。原因是 Windows **UIPI**：低完整性进程不能向高完整性窗口投递窗口消息（§2.2）。此外该路线的 `should_capture()` 恒为 `True`（§2.3）。
- **真实光标**：`SetCursorPos` + `SendInput`。走输入队列，**不受 UIPI 限制**（§2.2）。但要求窗口在前台，且不满足时 ok-ww 的 `sleep()` **没有正常出口**，会静默卡死整条链（§2.3）。

## 决策

1. **黑盒**：只做进程外操作，不改造 ok-ww 源码。
2. **只用真实光标**：不实现 `PostMessage` 路线。该路线作为已记录在案的不可用选项保留在文档中。
3. **操作方必须以管理员运行**：由此成为框架的硬前置（节点 1）。

## 考虑过的替代方案

**改造 ok-ww 源码**（白盒）。被否：ok-ww 是他人项目，改造费时费力，且黑盒框架对白盒同样适用，反之不成立。

**`PostMessage` 路线**。被否：UIPI 下对提权的 ok-ww 直接失败。若强行采用，需提升操作方完整性级别——那正是决策 3 已经要做的事，但即便如此，该路线换来的"免前台"收益，仍需与它对窗口消息语义的依赖一并承担。

> **勘误（后续实测）**：本条原写"该路线**必然失败**"。**该表述不准确**。实测表明，当**框架与 ok-ww 同为提权**时，`PostMessage(hwnd, WM_NULL, 0, 0)` **返回 `True`，投递成功**（见 FRAMEWORK §5.4）。真实规则是：投递成败取决于**双方完整性级别是否匹配**——框架更低则被 UIPI 拒绝，同级则允许。
>
> **决策不变，但理由收窄**：不采用投递路线，是因为**真实光标跨完整性行为一致、且不依赖窗口消息语义**（本 ADR 的正面理由），而**不是**因为"投递不可用"。错误归因会导致后人基于错误前提重新评估此决策。

**双路线并存（可配置）**。被否：两条路线的 `should_capture()` 语义相反，前台约束、权限模型、坐标可信度都不同，并存会把差异渗透进整个框架。既然真正可用的只有一条，就不为另一条留抽象。

## 后果

**正面**：
- 不受 UIPI 限制，操作能力不依赖窗口消息语义。
- 在所有完整性组合下行为一致，不必分支。

**负面，且必须承担**：
- **窗口必须在前台**（`GetForegroundWindow() == hwnd`），成为硬前置。
- 失焦时 ok-ww **静默挂起、无任何报错**，故障发现成本高。诊断"点了没反应"时，第一站永远是前台状态。
- 真实光标会**实际移动用户的鼠标**，与用户抢光标。
- 框架自身**必须以管理员运行**，否则连进程都清理不掉（实测非提权会话 `Stop-Process` → Access denied，§2.2）。
