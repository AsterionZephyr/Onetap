# 7. 文档分层与单一事实源：规则只写一处，摘要只留指针

日期：2026-10-23

## 状态

已接受。已按本决策完成一轮文档内容治理（4 个 commit：规则三分归位 / 术语表净化 / 档案层索引 / 门禁 C5–C7）。本文接续 [ADR 0006](0006-workspace-directory-contract.md) 里「内容治理留待后续轮次」那一条。

## 背景

ADR 0006 解决的是「东西在哪一层」，没碰「同一件事被说了几遍」。实测：

- **逐字重复很少**：正文行（≥40 字符）跨文件完全相同的只有 5 行，其中 4 行是 `README.md` 与 `RUNBOOK.md` 里同一批命令行。所以问题**不是复制粘贴**，是**各自换句话复述同一条规则**。
- **三份规则清单成员不同**：`AGENTS.md` 13 条、`docs/HANDOFF.md` §2.2 12 条、`docs/FRAMEWORK.md` §1 42 条。AGENTS 缺 HANDOFF 的第 8、12 条；HANDOFF 缺 AGENTS 的「超时必需 / UNKNOWN 不默认成功 / 时间戳基线闸 / 等待阶段不抓帧」四条。**改一处，另外两处不会报错**——这比复制粘贴更危险，因为三份都「看起来同步」。
- **AGENTS.md 膨胀**：124 行里，规则摘要 13 条 + 静默失效 7 条占了 29 行，全是 HANDOFF §2 的压缩版。
- **术语表混进实现**：`docs/CONTEXT.md` 里有模块路径、`Node(sid, name, label, why, has_args, shared)` 的元素结构、钩子参数表、`steps/chain.py` 的 `check_all()`——这些是交接书的内容，不是领域词汇。
- **档案层无索引**：`docs/FAULT-LOG.md` 2291 行 / 115 KB、`docs/HISTORY.md` 931 行 / 76 KB。FAULT-LOG 里混着大量**非故障章节**（处置方案、回归总览、`window.py` 改造、`cleanup.py` 参数化、每轮的「本轮做了什么」），而且 **#31–#37 七条故障在 FAULT-LOG 里 0 命中**，却被 33 个 `orchestrator/*.py` 与全仓 278 处引用指着。

一句话：**没有任何机制规定「这条知识该写在哪」，所以同一条知识被写进每个看起来合适的地方。**

## 决策

1. **三类知识分家**，各有唯一归属：
   - **可证伪的跨程序约束** → `docs/FRAMEWORK.md` §1，给编号 `INV-nn`，正文含「断言 + 依据 + 状态」。
   - **操作红线与静默失效陷阱** → `docs/HANDOFF.md` §2（§2.1 陷阱表 18 条、§2.2 十二条硬性规则）。
   - **历史、故障、实测经过** → `docs/HISTORY.md` 与 `docs/FAULT-LOG.md`，属**档案层**：只追加、不改写。
   - **领域术语** → `docs/CONTEXT.md`：只写「是什么 + 与相邻概念怎么区分」。
2. **单一事实源**：一条规则的正文**只存在一处**。其他位置只允许两种形态：**编号指针**（`INV-30`、`规则 7`、`FAULT #35`）或**一句结论 + 指针**。**禁止**在摘要里复述阈值、实测数字、失效后果。
3. **`AGENTS.md` 只写「先读哪、跑什么」**：目录表 + 4 条节点链/归属指令 + 3 条硬指令（读 §2 并跑回归、跑 pyflakes 与 selfcheck、Python 与提权）。不再出现任何阈值、实测数字、故障编号。
4. **`docs/CONTEXT.md` 不做实现索引**：模块路径、`Node(...)` 元素结构、钩子参数表、`check_all()` 全部搬进 `docs/HANDOFF.md` §5「模块划分」，术语条目只留一句「见 HANDOFF §5」。
5. **档案层加索引、正文不改写**：两份文件开头各加索引表（编号｜日期｜一句话结论｜状态｜跳转），FAULT-LOG 里的非故障章节按轮次**归位**到 HISTORY；已经写下的正文（含「更正」「已废弃」「结论被推翻」）保持原样。
6. **机器校验 C5–C7**（`probe/_check_workspace.py`，与目录契约 C1–C4 同一脚本）：C5 文档内部相对链接全部有效；C6「共 N 条」「十二条」这类声明与实际条目数一致；C7 所有 `INV-nn` / `硬性规则 n` / `FAULT #nn` 引用可解析（反向的孤儿条目只报不拦）。

## 理由

### 为什么保留编号指针，而不是把摘要全删

`AGENTS.md` 是新会话的必读入口。全删会让 agent 根本不知道「有一条 INV-30 管这件事」，于是重新造一个近似规则——这正是本次要消灭的模式。指针让人知道**去查哪一条**，不必记住正文。所以摘要保留「一句结论 + 编号」，删掉的是正文里那些会漂移的东西（阈值、窗口尺寸、实测分数）。

### 为什么档案层只加索引、不改写

`FAULT-LOG.md` 的叙事是**有依赖的**：FAULT #14 出现两次、第二次推翻第一次；#9 有「结论更正」；#27 有「我上一轮报的是错的」。重排或改写这些章节会把这些回指扯断，读者将无法判断哪条结论还有效。反过来，**索引能解决「找不到」**，而「找到以后发现结论过时」由索引的状态列（有效 / 已修复 / 已废弃 / 结论被推翻）解决。真要通读，那是「活结论上提」的另一个工程。

### 为什么否决「每份文档最后核实日期」

曾考虑给每份文档加一个「最后核实」字段（C8）。它自己就是一个新的漂移点：改内容的人不会记得改日期，而日期一旧，所有内容看起来都不可信。结构问题用结构校验，不用人工时间戳。

### 为什么必须机器校验（B 层）

本次三种漂移全部**不是笔误**：三份规则清单各缺条目、HANDOFF §2.1 抬头写着「第 12~16 条」而表里已有 18 条、AGENTS 与 README 都在描述已经删掉的目录。**人不会每次改完都回头核对数字**，脚本会。C6 专治「共 N 条」这类自我描述，C7 专治「引用了不存在的编号」。

## 后果

- **新增知识必须先选一处**：跨程序可证伪 → 在 FRAMEWORK §1 加 `INV-nn`；操作红线/陷阱 → HANDOFF §2.1 或 §2.2；其余一律写进 HISTORY / FAULT-LOG 并只回填指针。C6/C7 会拦住「共 N 条」不一致与悬空编号。
- **`AGENTS.md` 从 124 行降到 94 行**，且不再随规则增加而膨胀。
- **`docs/FAULT-LOG.md` 补齐 #26、#31–#37**（此前从未成文，却已被代码引用）；`docs/HANDOFF.md` §2.2 里 #35/#36 的两段内联正文缩成一行指针。
- **未做（另立项）**：HISTORY / FAULT-LOG 的**活结论上提**——把仍然有效的结论提炼进 FRAMEWORK / VERDICT，档案层只留过程。以及 `logs/` 的保留策略。
