# 6. 工作区目录契约：三层落位 + 机器校验

日期：2026-10-23

## 状态

已接受。已按本决策完成一轮整理，契约由 [`probe/_check_workspace.py`](../../probe/_check_workspace.py) 逐条校验（本决策对应 C1~C4；同一脚本另有 C5~C7 文档一致性判据，见 [ADR 0007](0007-doc-layering-single-source.md)，以及只提示不拦的 C8 日志保留检查。exit≠0 即违约），并列入 [ADR 0003](0003-per-program-app-modules.md) 的共用层回归清单第 8 条。

## 背景

整理前的工作区是 1552 个文件 / 60.5 MB，但**乱的不是体积，是「东西在哪一层」说不清**：

- `docs/` 里混着 **22 个 `_probe_*.py`** 和一张 `gui2-p1.png`（127 KB）。文档目录里放可执行脚本，改文档的人会以为那是文档。
- `probe/` 里 **79 个脚本**没有索引：18 个零引用且连 docstring 都没有，谁也不知道它证明过什么；剩下 61 个只有文件头一行字，`ls` 一遍看不出该跑哪个。
- 根目录堆过 `%SystemDrive%/`（未加引号的 `$env:SystemDrive` 造出来的 Windows 缓存转储）、`probe-shots/`、`debug.log`、`.dsh-tmp/gitversion.txt`、`probe/_pyout.txt`。这些都是**一次性事故现场**，不是项目内容。
- 同一份「十二条硬性规则」在 `AGENTS.md` / `docs/HANDOFF.md` §2 / `docs/FRAMEWORK.md` 各写一遍（内容治理留待后续轮次，见「后果」）。

一句话：**「哪些文件可以在根目录」「哪些东西可以住文档目录」从来没有成文契约，也没有任何东西在拦**。整理完不收口，下次一样会乱回去。

## 决策

1. **根目录只放三份文件**：`README.md`（项目门面）、`AGENTS.md`（新会话必读）、`.gitignore`。任何新增的顶层目录必须在 `README.md` 的「## 目录」表里有行。
2. **`docs/` 只放文档**：`.md` 文件 + `adr/`（决策记录）+ `img/`（文档引用的配图；目前为空 —— 原 `gui2-p1.png` 已作为过期资产删除）。**探针不进 `docs/`，配图不进 `docs/` 根**。
3. **一次性证据脚本全部单层放在 `probe/`**，并在 `probe/README.md` 里维护**一行一条的索引**（79 条，分「门禁 / 回归自检 / MaaEnd / ok-nte / ok-ww / GUI / 通用」七组，每行写清它证明什么）。不按程序或用途再分子目录。
4. **运行产物只在 `logs/`**（已 gitignore；保留策略是**只留最近十轮**，见 [`docs/RUNBOOK.md`](../RUNBOOK.md) §11，长期索引在 [`docs/RUN-INDEX.md`](../RUN-INDEX.md)）。任何脚本都不得把中间产物写到仓库根或 `docs/`。
5. 上述四条写进 `probe/_check_workspace.py`，**exit 0 才算合格**；改共用层时与自检一起跑。

## 理由

### 为什么探针必须单层、不能再分子目录

`docs/` 里那 22 个探针全部用 `Path(__file__).resolve().parent.parent`（或 `os.path.dirname(os.path.dirname(...))`）推仓库根再 `sys.path.insert`。搬到 `probe/`（与 `docs/` **同深度**）时这些脚本**一行代码都不用改**，只需改 38 处引用文档/代码里的路径。若在 `probe/` 下再建 `zmd/`、`gui/` 之类的子目录，这 22 个脚本（以及其他同样写法的脚本）会**全部 import 失败**——而失败现场是 `ImportError`，看起来像环境问题，排查成本远高于收益。**深度是契约的一部分**。

### 为什么要有 `probe/README.md` 索引，而不是「让脚本名说清楚」

删掉 19 个不可辨认的脚本只解决了「垃圾」，解决不了「看不懂」。79 个脚本里有 30 个零引用但自带 docstring——它们**有价值但没人知道该跑哪一个**。索引把「证明什么 / 怎么跑 / 多少行 / 还被谁引用」压成一行，才让这一层能被判断。反例：只删不索引，下次再想核对某个故障的证据时，还得把 79 个文件挨个 `head`。

### 为什么必须机器校验，而不是写进文档靠自觉

这次的乱本身就是「靠自觉」的产物：`.gitignore` 里早就写了 `probe-shots/`，根目录照样出现过四次不同的一次性产物；`AGENTS.md` 写着「根目录只留两份文件」，`README.md` 的目录表却把早已删除的目录继续列着。人不会每次都对着表格核对，脚本会。

## 后果

- **新增探针的硬性要求**：docstring 第一行写清「它证明什么 / 怎么跑」（`probe/README.md` 就是照这一行生成的）。没有这一行的脚本，下次整理会被当作零引用垃圾删掉。
- **探针不能再随意搬家**：它依赖「与仓库根隔一层」这个事实，动位置要连带改 `parent.parent` 或全部引用（本次 22 个搬运 + 38 处引用改写是**一次性的**，不必再做第二遍）。
- **门禁会挡住「临时丢个文件在根目录」**：这是设计意图。真需要临时文件，写 `logs/`（已 gitignore）。
- **未做**：文档**内容**治理（同一份规则三处重复、`docs/HISTORY.md` 76 KB / `docs/FAULT-LOG.md` 115 KB 的体量收敛）与 `logs/` 的保留策略，本轮只做「位置」不做「内容」。内容治理已由 [ADR 0007](0007-doc-layering-single-source.md) 接续；`logs/` 保留策略仍待下一轮。
